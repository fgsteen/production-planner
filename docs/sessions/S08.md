# S08 — Count line clears per campaign and make the plan respond to priorities

- **Date:** 2026-10-04
- **Goal:** Count line clears per campaign and make the plan respond to priorities

## Plan
- [x] Measurement script (`npm run measure:plan`)
- [x] One large line clear per campaign across weeks
- [x] A warm start the line clear weight steers
- [x] e2e: a higher line clear weight gives less line clear time
- [x] Solve progress and Cancel

## Log
- **User answers:**
  - goal as proposed in the handoff, plus an explanation of the warm start (given in chat);
  - **campaigns:** one large line clear per campaign, not per week;
  - **unmet demand beyond capacity:** fair share, every product short by about the same
    percentage. Recorded as R64; not built yet.
- **Measurement:** `scripts/measure/` has its own vitest config, outside `npm test` and `tsc`. It
  prints large clears, clear hours, U, unmet, pallets, gap and seconds per stage. Env vars
  `MEASURE_WEIGHTS` and `MEASURE_DEMAND` vary it.
  - **Baseline (S07 model):** weights 0, 4 and 10 gave 1,146, 1,041 and 1,043 large clears.
- **Model** ([ADR 0008](../decisions/0008-campaigns-across-weeks.md)):
  - `cont[p,m,w]` means a run continues from last week and needs no new large clear;
  - one product per machine crosses each week boundary;
  - a product running through a whole week runs alone in it, via an `alone[m,w]` binary.
  - **Fractional counts.** The first version, an aggregated big-M row, gave fractional line clear
    counts.
  - **Too many rows.** A per-pair version was exact but added 11,600 rows. The `alone` form needs
    about 2,800.
  - **Infeasible fix stage.** `alone ≤ 2 − Σ run` was infeasible once three or more runs were
    fixed; fixed with `n·alone + Σ run ≤ n + 1`, plus exact `alone` bounds once runs are fixed.
- **Warm start:**
  - **Dropped rule.** "Drop small weekly runs" broke campaigns, so higher weights gave *more*
    clears (759 → 871).
  - **New rule.** Low-volume pairs may only run every k-th week, with k from the weight, staggered
    per machine. Campaigns are halved if more than 0.1 % of demand goes unmet.
  - **Speed.** The relaxation leaves out `cont`: 7.3 s → about 2 s per LP.
- **UI:**
  - campaign wording;
  - "Line clear hours" in the summary;
  - the gap shows as "not proven" when HiGHS has no bound;
  - solve progress (step x of 3, with a timer) and a Cancel button;
  - a change during a solve now terminates the worker and starts again; before, it queued behind
    the stale solve.
- **Tests:**
  - **Unit:** a campaign across weeks pays one clear; three products with no storage give
    3 + 51 × 2 clears; `campaignCycles`.
  - **e2e:** weight 10 gives less line clear time than weight 0; progress, cancel and re-solve.

## Outcome
**Goal met.**

| Line clear weight | Large clears | Clear hours | Busiest machine | Time |
| --- | --- | --- | --- | --- |
| 0 | 754 | 3,121 | 70 % | 6.0 s |
| 4 | 635 | 2,811 | 77 % | 6.0 s |
| 10 | 676 | 2,691 | 91 % | 7.2 s |

The S07 model had about 1,040 large clears at weight 4.

- **Clear counts** need not fall with every weight step, because clear lengths differ per machine.
- **Higher demand:**
  - at 1.3× demand nothing is unmet now (S07: 0.2 %), but the solve takes 14 s;
  - at 2× demand 24 % is unmet, as before.
- **Not done:** R19 (max campaign length), now expressible; fair share for unmet demand (R64).
- **Tests:** `npm test` is green: tooling tests, typecheck, 77 unit tests and 24 e2e tests.
