# S04 — Recurring holidays, weekly demand input (ISO weeks), capacity check

- **Date:** 2026-10-04
- **Goal:** Recurring holidays, weekly demand input (ISO weeks), capacity check

## Plan
- [x] Recurring holidays and maintenance as `MM-DD` (R9), with migration of old files.
- [x] Demand input: yearly total per product, spread over ISO weeks, with pinned weeks (R20, R26).
- [x] Capacity check before any solver: shortfall, peak weeks, estimated machine load (R35).
- [x] Stretch: HiGHS spike, a first weekly LP plan in a Web Worker on a new Plan page (start of R21).

## Log
- **User decisions:**
  - Scope: demand and the capacity check, with the HiGHS spike only if there was time. There was.
  - Demand is a **yearly total divided over weeks**, using **Swedish (ISO 8601) week numbers**.
    The total spreads evenly, and chosen weeks can be **pinned**.
  - Units: pieces.
  - The planning year is the ISO week-year: 2027 = 2027-01-04 … 2028-01-02, 52 weeks.
  - Recorded in [ADR 0004](../decisions/0004-weekly-demand-iso-weeks.md). ADR 0003 now uses weeks
    as the period.
- **Model** ([src/model](../../src/model)):
  - `weeks.ts`: ISO week maths.
  - Holidays and maintenance are `MM-DD`, matched on month-day; `02-29` only counts in leap years.
  - `Dataset.demand`: `{ productId, yearlyUnits, weekOverrides }`. Validation catches pins above
    the total, a fully pinned year that doesn't sum to the total, weeks outside the year, and
    unknown products.
  - `parseDataset` upgrades pre-S04 files: no `demand` becomes `[]`, and `YYYY-MM-DD` loses its
    year. Malformed entries pass through untouched, so the error boundary still handles them;
    the recovery e2e test caught this.
  - `demand.ts`: `weeklyDemand` and `checkCapacity`:
    - per product per week: max output with all capable machines dedicated to it;
    - weeks over that max, i.e. stock must be built earlier;
    - **shortfall**: the largest cumulative gap, which no build-ahead can fix;
    - estimated machine load: demand split across machines in proportion to their output.
  - Demo data now has demand. Machine loads are 74–90 %. P07 has a pinned summer peak in
    weeks 22–33.
- **UI:**
  - Demand page (`#demand`):
    - summary tiles;
    - a product capacity check table and machine load bars;
    - a weekly grid (weeks × products) with editable yearly totals and week cells. Typing pins
      a week; clearing the cell unpins it. Pinned cells are bold; red cells exceed that week's max;
    - demand validation errors are shown on the page.
  - Numbers in the grid are space-grouped (`115 385`), so the decimal-comma parser reads them back.
  - Holiday and maintenance cells take `MM-DD`; a full date loses its year.
  - The overview counts shifts over the ISO week-year.
- **HiGHS spike** ([src/plan](../../src/plan)):
  - `lp.ts` builds a continuous LP as CPLEX LP text: hours per product × machine × week, one
    stock per product, and penalised unmet demand;
  - `solve.ts` runs it, and `plan.worker.ts` hosts it in a Web Worker;
  - the Plan page (`#plan`) re-solves on every data change. The demo data solves in ~65 ms,
    optimal, with no unmet demand;
  - the 3.5 MB wasm only loads when the Plan page opens;
  - ADR 0003 is now **accepted**, with the spike results;
  - observation: minimising machine-hours fills the faster A machines to 100 % and leaves B1 at
    about 15 %. The priority weights (R22) and transport are needed.
- **Housekeeping:** a `.obsidian/` folder (the user's vault settings) slipped into a commit via
  `git add -A`. It is now untracked and in `.gitignore`.
- **Tests:**
  - unit tests: ISO weeks, the weekly spread, demand validation, capacity check, demand reducer
    actions, the pre-S04 migration, recurring and leap-day holidays, and the LP (faster machine
    first, unmet demand, demo plan within shift limits);
  - e2e: demand page (demo, pin/unpin, shortfall, problems, reload), plan page (optimal, unmet
    demand after a change), updated holiday test.

## Outcome
- The goal and the stretch goal are done:
  - demand can be entered per ISO week, and capacity problems show before any solver runs;
  - a first LP plan is computed in the browser.
- Not done: line clears and integer lots, storage, trucks and priorities in the model. These are
  S05.
- `npm test`: green. That is 5 tooling tests, typecheck, 51 unit tests and 17 e2e tests.
